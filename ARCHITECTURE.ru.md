## Обзор системы

FuseDB разбивает пространство ключей на упорядоченное множество листьев. Лист
владеет полуоткрытым диапазоном ключей, in-memory буфером мутаций и не более чем
одним иммутабельным сегментом на диске. Каждый лист мерджится независимо, поэтому
объём, переписываемый одним merge, ограничен размером листа, а не размером базы
данных.

Публичная точка входа — `pkg/oneleafdb` (`DB`, `OpenDB`).

### Основные компоненты

**Дерево листьев** (`internal/tree`)
Упорядоченное множество листьев одной директории базы данных. Публикуется по
принципу copy-on-write (COW) через `atomic.Pointer`, ищется бинарным поиском и
структурно изменяется только под одним мьютексом, который не берут ни чтения, ни
обычные записи.

**Лист** (`internal/leaf`)
Один диапазон ключей: двухслойный буфер мутаций плюс атомарно подменяемый reader
сегмента. Владеет проходом merge/split по собственным данным.

**Skiplist-буфер** (`internal/skiplist`)
Lock-free упорядоченный индекс, хранящий последние мутации. Поддерживает операции
Put, Delete и Inc с in-place слиянием для счётчиков.

**Сегмент** (`internal/segment`)
Иммутабельная структура на диске, содержащая блоки данных, bloom filter, индекс
блоков и метаданные. Записывается один раз при merge, никогда не модифицируется.

**Write-Ahead Log** (`internal/wal`)
Append-only лог из пронумерованных записей с контрольными суммами и групповым
коммитом. Читаемый: поддерживает воспроизведение (replay), восстановление после
оборванного хвоста и усечение после checkpoint.

**Манифест** (`internal/manifest`)
Персистентный каталог: диапазоны листьев, идентификаторы и версии сегментов, а
также watermark лога, уже покрытый сегментами. Переписывается целиком и атомарно
при каждом обновлении.

**Компрессия** (`internal/compression`)
Опциональная словарная LZ4-компрессия с персистентным реестром. Словари обучаются
оффлайн на репрезентативных сэмплах и хранятся как `.zdict` файлы.

**Кэш** (`pkg/oneleafdb/cache.go`)
Map-based кэш значений с шардированной инвалидацией по эпохам. Вытесняет
произвольные записи при превышении бюджета в байтах.

### Принципы дизайна

- Иммутабельность: сегменты никогда не модифицируются после создания
- Lock-free чтение: ни поиск, ни обычная буферизованная запись не берут блокировку
- Локальный merge: переписывается только тот лист, который перешёл свой порог
- Copy-on-write структура: слайс листьев заменяется целиком, а не правится на месте
- Zero-copy: пулы буферов минимизируют аллокации
- Словарная компрессия: предобученные LZ4-словари для маленьких блоков

### Ключевые ограничения

Пустой ключ отвергается методами `Tree.Put`, `Tree.Delete` и `Tree.Inc` с ошибкой
`ErrEmptyKey`. Пустой ключ не может быть разделителем блоков в индексе сегмента
(`ErrEmptySeparator`), а пустой нижний ключ уже означает «самый левый лист», так
что его приём всплыл бы позже как merge, падающий для всего листа.

## Дерево листьев

Файл: `internal/tree/tree.go`

### Структура

Листья хранятся в отсортированном слайсе, публикуемом через атомарный указатель:

```go
type Tree struct {
    leaves atomic.Pointer[[]*leaf.Leaf]
    gen    atomic.Uint64
    mu     sync.Mutex
    manifest *manifest.Manifest
    // ...
}
```

Лист покрывает `[LowKey, LowKey следующего листа)`; последний лист не ограничен
справа, а самый левый имеет пустой `LowKey`, поэтому вместе листья покрывают всё
пространство ключей без дыр. Лист никогда не расширяется и не сужается: при split
он заменяется новыми листьями.

Множество листьев остаётся небольшим даже для очень большой базы данных — именно
поэтому используется отсортированный слайс, а не конкурентное B-дерево. При
значении по умолчанию 64 MiB на лист терабайт данных — это примерно шестнадцать
тысяч указателей.

### Поиск

`findLeaf` возвращает последний лист, нижний ключ которого не больше искомого:

```go
func searchLeaf(leaves []*leaf.Leaf, key []byte) int {
    lo, hi := 0, len(leaves)
    for lo < hi {
        mid := int(uint(lo+hi) >> 1)
        if bytes.Compare(leaves[mid].LowKey(), key) <= 0 {
            lo = mid + 1
        } else {
            hi = mid
        }
    }
    return lo - 1
}
```

### Счётчик поколений

`Tree.Get` не берёт блокировок. Вместо этого он обрамляет поиск поколением merge.
`gen` нечётен, пока результат merge устанавливается, и увеличивается по обе стороны
этого окна, так что поиск, увидевший «разорванное» состояние, наблюдает другое
поколение и повторяет попытку.

```go
gen := t.gen.Load()
if gen&1 != 0 { runtime.Gosched(); continue }

target := t.leafFor(key)
value, ok, err := target.Get(key)
if t.gen.Load() == gen {
    return value, ok, err
}
```

### Повтор записи

Буферизованные записи берут read-сторону write-блокировки листа, поэтому писатели
не блокируют друг друга. `TryPut` / `TryDelete` / `TryInc` возвращают false, если
лист был отсоединён при split, — это говорит дереву разрешить ключ по обновлённому
множеству листьев и повторить попытку. Повтор завершается, потому что split
публикует свои новые листья до того, как отпустит блокировку, отвергшую запись.

### Опции

| Опция | По умолчанию | Смысл |
|---|---|---|
| `MaxLeafBytes` | `64 MiB` | размер слитого payload, при котором merge начинает новый выходной сегмент, а вместе с ним и новый лист |
| `MergeThresholdBytes` | `8 MiB` | размер буферизованного payload, делающий лист кандидатом на merge |
| `TargetBlockSize` | `4 KiB` | целевой размер одного закодированного блока сегмента |
| `BloomFalsePositive` | `0.01` | целевая доля ложных срабатываний bloom filter |
| `Compression` | `CompressionNone` | `CompressionLZ4Dict`, когда передан словарь |
| `Seed` | задаётся вызывающим | подмешивается в выбор высоты в skiplist; переиспользуется выходами split |

## Формат сегмента

Файлы: `internal/segment/segment_file.go`, `header.go`/`header_codec.go`,
`footer.go`/`footer_codec.go`, `index.go`/`index_codec.go`,
`block.go`/`block_codec.go`, `bloom_filter.go`

### Раскладка

```
[Header][Data Blocks][Bloom Filter][Index][Footer]
```

Границы секций проверяются при открытии: секция bloom должна начинаться ровно там,
где заканчивается секция данных, индекс — там, где заканчивается bloom, а footer
должен заканчиваться на размере файла (`validateSegmentLayout`).

Сегменты именуются `segment-<id>-v<version>.seg` (оба числа дополняются нулями до
20 цифр). Они пишутся в соседний `.tmp` файл и становятся видимыми только при
`Freeze`, который синхронизирует файл, переименовывает его и синхронизирует
директорию.

**Header** (28 байт)

```
[magic "FHDR":4][format version:4][segment version:8][compression:4][dictionary id:4][crc32:4]
```

Версия формата — 3. Идентификатор словаря должен быть нулевым для сырого сегмента и
ненулевым для сегмента с LZ4-словарём.

**Data Blocks** (переменная длина)
Последовательность независимо закодированных блоков. При `CompressionLZ4Dict`
каждый закодированный блок сжимается целиком и оформляется как
`[uncompressed size:4][LZ4 payload]`. При `CompressionNone` закодированный блок
хранится как есть.

**Bloom Filter** (переменная длина)

```
[magic "FBLM":4][version:4][numBits:4][numHashes:4][bitset length:4][bitset][crc32:4]
```

Фильтр реализован в этом репозитории (`internal/segment/bloom_filter.go`), а не
взят из внешнего пакета. Это классический `m`/`k` bloom filter, размер которого
рассчитывается по ожидаемому количеству ключей и целевой доле ложных срабатываний,
с двойным хэшированием: `h1 = xxhash.Sum64(key)` и `h2 = splitmix64(h1 ^ φ)`, где
бит `i` находится по адресу `(h1 + i*h2) mod numBits`.

**Index** (переменная длина)

```
[entry count:4] далее на запись: [separator length:4][separator][offset:8][length:4]
```

В памяти:

```go
type BlockIndexEntry struct {
    Separator []byte // inclusive upper bound of the block key range
    Offset    uint64 // relative to the start of the data section
    Length    uint32 // encoded (and compressed) block length
}
```

Точечный поиск находит первую запись, разделитель которой больше или равен искомому
ключу. Записи должны быть отсортированы по разделителю и не должны пересекаться.

**Footer** (64 байта)

```
[magic "FFTR":4][version:4][block count:4][Data section:16][Bloom section:16][Index section:16][crc32:4]
```

Каждая секция — это `[offset:8][length:8]`.

### Структура блока

Один закодированный блок с контрольной суммой CRC-32 (IEEE):

```
[magic "FBLK":4][version:4][entry count:4]
  на запись: [keyLen:4][valueLen:4][key][value]
  таблица смещений: [entry offset:4] * entry count
[crc32:4]
```

Именно завершающая таблица смещений делает блок адресуемым в произвольном порядке:
`BlockView` выполняет бинарный поиск по записям, не декодируя блок, а payload
записи ограничивается следующим смещением.

Целевой размер блока — 4 KiB (`DefaultTargetBlockSize`). Писатель сбрасывает текущий
блок перед добавлением записи, которая вывела бы его за целевой размер, поэтому блок
может превысить цель только тогда, когда одна запись сама больше цели.

### Алгоритм чтения

1. Проверить общесегментный bloom filter; отрицательный ответ завершает поиск
2. Бинарным поиском по индексу в памяти найти блок, разделитель которого покрывает ключ
3. Прочитать байты блока в пуловый буфер
4. Декомпрессировать LZ4-словарём, если сегмент сжат
5. Выполнить бинарный поиск по блоку через `BlockView.Find`

Путь в коде: `Reader.Get`, `Reader.readBlockValue`, `BlockView.Find`.

## Система компрессии

Файлы: `internal/compression/dict.go`, `dict_file.go`

Компрессия опциональна и задаётся на весь сегмент. `OpenDB` использует
`CompressionNone`, если в `DBOptions.Dictionary` не передан словарь; в противном
случае каждый блок каждого вновь записываемого сегмента сжимается с
`CompressionLZ4Dict`.

### Обучение словаря

Словари обучаются оффлайн с помощью `github.com/klauspost/compress/dict`:

```go
raw, err = dictbuilder.BuildRawDict(samples, dictbuilder.Options{
    MaxDictSize: opts.Size, // default 4 KiB
    HashBytes:   6,
})
```

Обучение извлекает общие паттерны из сэмпл-данных. На корпусе и машине,
зафиксированных в `benchmarks/RESULTS.md` (данные от 2026-05-11, до переписывания на
дерево листьев), 4 KiB LZ4-словарь экономил 62.6% байтов блоков.

Путь в коде: `TrainDictionary`.

### Формат персистентности

Словари хранятся как `.zdict` файлы (`dict-%08d.zdict`), записываемые атомарно:

```
[Magic:4][Version:4][ID:4][Level:4][RawLen:4][CRC32:4][RawBytes]
```

Magic: `"FDDC"`
Version: 1
ID: уникальный идентификатор, должен быть ненулевым
Level: LZ4-ускорение (acceleration), используемое кодеком
RawLen: размер словаря в байтах
CRC32: IEEE-контрольная сумма только по сырым байтам словаря
RawBytes: данные словаря

Путь в коде: `EncodeDictionary`, `DecodeDictionary`.

### Пайплайн компрессии

**Сжатие:**
1. `LZ4_createStream()` — инициализация потока
2. `LZ4_loadDict(dict)` — загрузка словаря
3. `LZ4_compress_fast_continue(src, dst, acceleration)` — сжатие блока
4. Добавление 4-байтового заголовка с несжатым размером

**Декомпрессия:**
1. Чтение 4-байтового заголовка с несжатым размером
2. Взятие буфера из пула (5 KiB) или аллокация, если блок больше
3. `LZ4_decompress_safe_usingDict(src, dst, dict)`
4. Возврат пулового буфера; вызывающий обязан вызвать `Release()`

Путь в коде: `Dictionary.CompressInto`, `Dictionary.Decompress`.

### Реестр

LRU-кэш загруженных словарей:

```go
type Registry struct {
    dicts map[uint32]*registryEntry
    lru   *list.List
    limit int
    fs    disk.FS
    dir   string
}
```

При запросе словаря (`MustGet`):

1. Проверить in-memory map и переместить запись в начало LRU-списка
2. Если записи нет, а у реестра настроено хранилище, загрузить её с диска
3. Вытеснить наименее недавно использованную запись при превышении лимита

## Реализация skiplist

Файл: `internal/skiplist/skiplist.go`

### Структура

```go
type node struct {
    key  []byte
    op   atomic.Pointer[ops.Op]
    next []atomic.Pointer[node]
}
```

Lock-free дизайн на атомарных указателях. Максимальная высота: 20 уровней. Удаления
представлены tombstone; узлы никогда не отсоединяются физически.

### Выбор высоты

Детерминированный, выводится из хэша ключа и seed списка:

```go
func (s *SkipList) randomHeight(key []byte) int32 {
    var h int32 = 1
    hash := xxhash.Sum64(key) ^ s.seed

    for h < maxHeight && (hash&3) == 0 {
        h++
        hash >>= 2
    }
    return h
}
```

Вероятность: 25% шанс каждого дополнительного уровня. Один и тот же ключ всегда
получает одну и ту же высоту в пределах одного списка.

### Алгоритм вставки

1. Считать текущую высоту списка
2. Найти splice: определить узлы-предшественники на всех уровнях
3. Если ключ уже существует, обновить его Op на месте и выйти
4. Опубликовать уровень 0 через CAS, повторяя весь цикл при конфликте
5. Опубликовать верхние уровни, переопределяя splice поуровнево при конфликте
6. При необходимости атомарно увеличить высоту списка

```go
func (s *SkipList) Apply(key []byte, op ops.Op) {
    for {
        oldHeight := s.height.Load()
        s.findSplice(key, &prevList, &nextList)

        if next := nextList[0]; next != nil && bytes.Equal(next.key, key) {
            s.updateNode(next, op)
            return
        }

        nodeHeight := s.randomHeight(key)
        s.prepareNewLevels(oldHeight, nodeHeight, &prevList, &nextList)

        newNode := newNode(key, op, nodeHeight)
        if !s.publishBaseLevel(newNode, &prevList, &nextList) {
            continue
        }

        s.publishUpperLevels(key, newNode, nodeHeight, &prevList, &nextList)
        s.growHeight(oldHeight, nodeHeight)
        return
    }
}
```

Высоту нужно считывать *до* `findSplice`. `findSplice` заполняет уровни ниже той
высоты, которую он увидел; чтение большей высоты после этого заставило бы
`prepareNewLevels` считать промежуточные уровни уже заполненными, и тогда
`publishUpperLevels` разыменовал бы nil-предшественника.

### Алгоритм обновления

Когда ключ существует, указатель Op заменяется на месте без переподключения:

```go
func (s *SkipList) updateNode(n *node, op ops.Op) {
    for i := 0; ; i++ {
        oldPtr := n.op.Load()
        merged := coalesceToNew(*oldPtr, op)

        if n.op.CompareAndSwap(oldPtr, &merged) {
            s.dataBytes.Add(int64(len(merged.Data) - len(oldPtr.Data)))
            return
        }
        if i&7 == 7 {
            runtime.Gosched()
        }
    }
}
```

Периодический `Gosched` не даёт конкурентному CAS-циклу заморить ту горутину,
которая позволила бы ему продвинуться.

### Слияние операций

Операции Inc сливаются, чтобы уменьшить расход памяти:

```go
func coalesceToNew(old, next ops.Op) ops.Op {
    switch next.Kind {
    case ops.OpPut, ops.OpDelete:
        return next
    case ops.OpInc:
        if old.Kind == ops.OpInc {
            sum := ops.DecodeInc(old) + ops.DecodeInc(next)
            return ops.NewInc(sum)
        }
        return next
    default:
        return next
    }
}
```

## Буфер листа

Файл: `internal/leaf/buffer.go`

Буфер листа держит два skiplist — активный, принимающий новые записи, и
замороженный, который сейчас выписывает merge, — за одним атомарным указателем:

```go
type layers struct {
    active *skiplist.SkipList
    frozen *skiplist.SkipList
}
```

Хранение обоих в одном значении и делает заморозку атомарной для читателей. При
раздельных указателях читатель мог бы застать момент между «активный заменён» и
«замороженный опубликован» и не найти ключ ни в одном слое, что читается как
отсутствующий ключ, а для счётчика — как потерянный инкремент.

| Метод | Эффект |
|---|---|
| `Freeze` | переносит активный слой в слот frozen и ставит свежий активный список; возвращает false, если замороженный слой уже есть |
| `ClearFrozen` | сбрасывает замороженный слой после успешного merge |
| `TakeActive` | подставляет свежий активный список и возвращает предыдущий; используется при передаче данных во время split |
| `ReadOp` | читает оба слоя из одного снимка и объединяет результат |
| `IterFrozen` | упорядоченный zero-copy итератор по замороженному слою, потребляемый merge |

`ReadOp` объединяет слои по тому же правилу, которое skiplist использует внутри
одного слоя: Put или Delete верхнего слоя побеждает безоговорочно, а Inc верхнего
слоя добавляется к Inc нижнего, а не заменяет его.

`Len` считает только активный слой, поэтому сразу после заморозки он читается как
ноль, хотя замороженным операциям ещё предстоит попасть в сегмент. Решения о merge
вместо этого используют `Leaf.PendingLen` (активный + замороженный).

## Write-Ahead Log

Файлы: `internal/wal/wal.go`, `format.go`, `reader.go`

По умолчанию лог располагается в `<dir>/wal.log`. Каждая запись несёт присвоенный
WAL порядковый номер и контрольную сумму, поэтому лог, записанный процессом,
убитым посреди записи, может быть воспроизведён вплоть до последней целой записи.

`DBOptions.DisableWAL` запускает работу без лога; эта опция существует для
бенчмарков, измеряющих только storage engine, и не является поддерживаемым режимом
для реальных данных.

### Заголовок файла

```
[magic "FWAL":4][format version:4][baseSeq:8][crc32c:4]
```

`baseSeq` — порядковый номер первой записи, которую может содержать файл. Он
сдвигается вперёд, когда лог усекается после checkpoint.

### Формат записи

```
[kind:1][seq:uvarint][keyLen:uvarint][payloadLen:uvarint][key][payload][crc32c:4]
```

Kind равен 1 (put), 2 (delete) или 3 (inc). Значения начинаются с 1, чтобы нулевой
байт никогда не был корректным началом записи: последовательность нулей в оборванной
или преаллоцированной области отвергается, а не декодируется в правдоподобную
запись.

Длины и порядковый номер кодируются varint, поэтому типичная запись тратит три
байта заголовка вместо двадцати, которые потребовались бы при фиксированной
раскладке. Конец записи остаётся однозначным, потому что декодер узнаёт обе длины
до того, как прочитает хоть одно поле переменного размера. Контрольные суммы
используют полином Кастаньоли, у которого есть аппаратная поддержка на amd64/arm64;
это важно, потому что лог считает контрольную сумму для каждой мутации на пути
записи.

Путь в коде: `appendRecord`.

### Групповой коммит

`Append` складывает закодированную запись в in-memory буфер под мьютексом и
присваивает следующий порядковый номер. Одна фоновая горутина владеет файловым
дескриптором и обслуживает три события:

```go
func (w *WAL) run() {
    ticker := time.NewTicker(w.groupEvery) // default 200µs
    for {
        select {
        case <-ticker.C:
            _ = w.flushActive()
        case request := <-w.flushCh:
            request.done <- w.flushActive()
        case request := <-w.rotateCh:
            request.done <- w.rotate(request.upToSeq)
        case <-w.stop:
            err := w.flushActive()
            w.done <- w.closeFile(err)
            return
        }
    }
}
```

`flushActive` подменяет staging-буфер, записывает его по отслеживаемому смещению в
файле и вызывает `Sync`.

### Режимы синхронизации

**Async (по умолчанию):** `Append` возвращается сразу, как только запись
подготовлена в буфере. Долговечность достигается на следующем групповом коммите,
при явном `Sync` или при `Close`.
**Sync (`SyncWrites`):** `Append` запрашивает сброс и ждёт его.

### Чтение и восстановление

`Cursor`, `Iterate` и `ReadAll` проходят лог с начала. Курсор останавливается на
первой записи, которую он не может проверить:

- если это последняя запись, итерация завершается штатно, и `Result` сообщает
  `TruncatedTail` с `ValidEnd`, указывающим сразу за последнюю целую запись, — это
  ожидаемое состояние после аварии, а не повреждение
- если она находится раньше в файле, итерация падает с `ErrCorruptRecord` или
  `ErrSequenceGap`

`Open` выполняет этот проход первым делом. Оборванный хвост физически отбрасывается
переписыванием файла, поэтому оставшиеся байты прерванной записи никогда не будут
приняты за запись на следующем проходе.

### Усечение

`Truncate(upToSeq)` отбрасывает записи с номером не выше `upToSeq`. Уцелевшие
переписываются в новый файл, заголовок которого объявляет `baseSeq = upToSeq+1`.
Замена устанавливается через временный файл, атомарное переименование и
синхронизацию директории, поэтому авария в любой момент оставляет на месте либо
старый, либо новый — но целый — лог.

## Манифест

Файлы: `internal/manifest/manifest.go`, `manifest_codec.go`

Манифест — персистентный каталог, позволяющий переоткрыть существующую базу данных,
а не перестраивать её и не отказывать в открытии. Он хранится как `MANIFEST` в
директории базы данных.

```go
type Manifest struct {
    NextSegmentID uint64 // segment id allocator; 0 is reserved for "no segment"
    AppliedSeq    uint64 // highest WAL sequence number durable in these segments
    Leaves        []LeafRecord // sorted strictly ascending by LowKey
}

type LeafRecord struct {
    LeafID         uint64
    LowKey         []byte
    SegmentID      uint64
    SegmentVersion uint64
}
```

Диапазоны листьев полуоткрыты, и хранится только нижняя граница: лист покрывает
`[LowKey, LowKey следующего листа)`, а последний лист покрывает всё, что правее.
Нулевой `SegmentID` означает, что у листа ещё нет сегмента, — это корректное
состояние только что созданного пустого листа.

### Раскладка на диске

```
header:  [magic "FMAN":4][format version:4]
body:    [NextSegmentID:8][AppliedSeq:8][leaf count:4]
         на лист: [LeafID:8][SegmentID:8][SegmentVersion:8][low key length:4][low key]
trailer: [crc32:4]   // IEEE, over the body only
```

Нижние ключи снабжены префиксом длины, а не разделителями, поэтому пустые ключи и
ключи с произвольными байтами, включая NUL, проходят кодирование и декодирование без
изменений.

### Стратегия обновления

Манифест переписывается целиком при каждом обновлении через
`disk.WriteFileAtomically`. Это сделано намеренно: манифест содержит самое большее
тысячи записей о листьях, поэтому полная перезапись обходится намного дешевле
append-only журнала правок с периодической компакцией, и при этом каждое состояние
на диске оказывается самодостаточным снимком с проверкой CRC. Если количество
листьев когда-нибудь перерастёт этот масштаб, пересматривать следует именно это
решение.

### Инварианты

`Validate` выполняется перед каждым сохранением и после каждой загрузки:

- листья строго возрастают по нижнему ключу
- идентификаторы листьев уникальны
- пустой нижний ключ может быть только у первого листа
- непустое множество листьев обязано начинаться с пустого нижнего ключа, чтобы ни
  одна часть пространства ключей не осталась непокрытой

## Merge и split

Файлы: `internal/tree/merge.go`, `internal/leaf/split.go`, `internal/leaf/merger.go`

### Триггер

Каждая запись уведомляет фоновый воркер через канал на один слот. Воркер решает,
какая работа сейчас нужна:

```go
func (db *DB) runMergeCycle() error {
    if db.walBytes.Load() >= db.checkpointBytes { // default 64 MiB
        return db.checkpoint()
    }
    if db.tree.BufferedBytes() < db.thresholdBytes { // default 8 MiB
        return nil
    }
    return db.mergeLeaves()
}
```

`mergeLeaves` мерджит только те листья, которые вернул `Tree.PendingMerge`, — те,
чей буфер перешёл `MergeThresholdBytes`, плюс любой лист, чей предыдущий merge
упал после заморозки буфера, — и затем сохраняет манифест. Он намеренно не двигает
watermark лога: слиты были лишь некоторые листья, поэтому записи для остальных
всё ещё нужны.

Первая ошибка фонового merge сохраняется и всплывает при следующем пользовательском
вызове, поэтому сломанный merge не может выглядеть как здоровая база данных, которая
тихо перестала мерджиться.

### Merge одного листа

`Tree.MergeLeaf` удерживает структурный мьютекс на протяжении всего прохода:

1. Проверить, что лист всё ещё входит в опубликованное дерево; лист, заменённый
   более ранним split, игнорируется, поэтому вызывающий может передать список
   листьев, собранный раньше
2. Заморозить буфер листа
3. Построить слитый поток: `Merger.MergeIter` идёт по итератору сегмента и итератору
   замороженных операций синхронно, разрешая Put, Delete и Inc относительно значения
   из сегмента
4. Записать результат потоком в выходные сегменты (см. ниже)
5. Сохранить манифест, затем установить результат

Итератор исходного сегмента опрашивается через `IterWithErr`. Без проверки этого
аксессора один нечитаемый блок молча отбросил бы все оставшиеся ключи, а усечённый
результат затем заменил бы исправный сегмент.

### Split

`Leaf.MergeSplit` режет выход по накопленным байтам payload, а не по заранее
вычисленной медиане, — именно это делает merge однопроходным: источник читается один
раз, а новый выход начинается, как только текущий заполнен.

```go
func (b *splitBuilder) add(key, value []byte) error {
    if b.current != nil && b.opts.MaxBytes > 0 && b.currentBytes >= b.opts.MaxBytes {
        if err := b.closeCurrent(); err != nil {
            return err
        }
        b.nextLow = bytes.Clone(key)
    }
    // ... open the next output if needed, then append
}
```

Разрез приходится на границу ключей, поэтому выход может превысить `MaxLeafBytes`
максимум на одну запись. Первый ключ следующего выхода становится включающей нижней
границей этого листа.

Идентичности сегментов выделяются в порядке выходов. Первый выход продолжает
диапазон, которым лист уже владеет, поэтому он сохраняет идентификатор сегмента и
лишь переходит на следующую версию; каждый последующий выход получает свежий
идентификатор с версией 1.

При любой ошибке все произведённые к этому моменту выходы удаляются, поэтому упавший
merge не оставляет после себя частичных сегментов. Идентификаторы сегментов,
израсходованные неудачной попыткой, не переиспользуются: остаточный файл от частично
неудавшегося удаления никогда не должен попасться более позднему merge.

### Расчёт размера bloom filter

Каждый выход рассчитывается на полное количество слитых ключей:

```go
expectedKeys := l.segmentKeys.Load() + l.buffer.FrozenLen()
```

Расчёт по одному только буферу, как делал прежний путь с единственным сегментом,
ухудшает фильтр понемногу с каждым merge. Лист, переоткрытый из манифеста, стартует
с `segmentKeys == 0`, потому что файл сегмента не хранит количество своих ключей,
поэтому первый merge после переоткрытия рассчитывает фильтр только по буферу.

### Установка результата

| Выходы | Путь | Эффект |
|---|---|---|
| 0 | `installEmptyLocked` | все ключи разрешились в tombstone; лист сохраняет диапазон и теряет сегмент |
| 1 | `installMergeLocked` | лист сохраняет идентичность, буфер и место в дереве; меняется только сегмент под ним |
| >1 | `installSplitLocked` | лист заменяется одним листом на каждый выход |

Именно порядок публикации при split не даёт потерять записи. Сначала строятся новые
листья и сохраняется манифест, пока писатели всё ещё используют старый лист. Затем,
под write-блокировкой старого листа, операции, буферизованные после заморозки merge,
маршрутизируются в новые листья, и только после этого новые листья публикуются.
Публикация в первую очередь позволила бы свежей записи попасть в новый лист, а затем
быть перезаписанной более старой воспроизведённой операцией для того же ключа.

### Вывод сегментов из эксплуатации

Заменённый reader не закрывается немедленно: поиски не берут блокировок, поэтому
какой-то из них может уже находиться внутри сегмента. Reader'ы попадают в очередь,
которую разбирает один воркер на дерево (`internal/tree/retire.go`); он закрывает
reader и удаляет файл по истечении TTL в 2s, проверяя очередь каждые 100ms. Один
общий воркер заменяет собой горутину на каждый лист, которая иначе потребовалась бы
дереву из тысяч листьев.

## Восстановление и checkpoints

Файл: `pkg/oneleafdb/db.go`

### Открытие базы данных

`OpenDB` восстанавливает базу данных с диска:

1. Загрузить `MANIFEST`. Отсутствие файла — нормальное состояние свежей директории;
   в этом случае получается новое дерево с одним пустым листом, покрывающим всё
   пространство ключей
2. `tree.Open` переоткрывает сегмент каждой записи о листе, где сегмент указан,
   пересобирает множество листьев в сохранённом порядке и продолжает выделение
   идентификаторов листьев после максимального найденного
3. Открыть write-ahead log, что отбрасывает оборванную последнюю запись, если она есть
4. Воспроизвести хвост лога

```go
func (db *DB) replayWAL(path string, appliedSeq uint64) error {
    _, err := wal.Iterate(db.fs, path, func(record wal.Record) error {
        if record.Seq <= appliedSeq {
            return nil
        }
        switch record.Kind {
        case ops.OpPut:    return db.tree.Put(record.Key, record.Payload)
        case ops.OpDelete: return db.tree.Delete(record.Key)
        case ops.OpInc:    return db.tree.Inc(record.Key, ops.DecodeInc(record.Op()))
        }
        // ...
    })
    // ...
}
```

Записи с номером не выше `AppliedSeq` уже durable в сегментах; их воспроизведение
удвоило бы каждый содержащийся в них инкремент.

### Checkpoints

Checkpoint — это то, что двигает watermark и позволяет усечь лог. Он запускается
`DB.Merge`, `Close`, а также фоновым воркером, как только лог вырос больше
`WALCheckpointBytes`.

```go
func (db *DB) checkpoint() error {
    db.applyMu.Lock()
    watermark := db.walLastSeq()
    db.tree.FreezeAll()
    db.applyMu.Unlock()

    if err := db.tree.MergeAll(); err != nil { /* ... */ }

    db.tree.SetAppliedSeq(watermark)
    if err := db.tree.SaveManifest(); err != nil { /* ... */ }
    if err := db.walTruncate(watermark); err != nil { /* ... */ }
    db.walBytes.Store(0)
    return nil
}
```

### Точный барьер

`applyMu` упорядочивает записи в лог относительно заморозки буферов. Писатели
удерживают read-сторону на протяжении «дописать в лог, применить к дереву»;
checkpoint берёт write-сторону ровно настолько, чтобы прочитать последний порядковый
номер и заморозить буфер каждого листа.

Это делает записанный watermark точным: каждая операция с номером не выше него
находится в замороженном множестве, и ничего выше него там нет. Watermark, отстающий
от данных, воспроизвёл бы инкремент, уже содержащийся в сегменте, и молча удвоил бы
его. Чтение порядкового номера и заморозка должны происходить в одном и том же окне
взаимного исключения — листья, созданные после заморозки, не покрыты, и это вторая
причина, по которой писатели удерживаются на обоих шагах.

Далее `MergeAll` мерджит каждый лист, у которого есть отложенные операции. Он
использует `PendingLen`, а не `BufferedLen`: после `FreezeAll` активный слой пуст,
тогда как замороженные операции ещё нужно записать, и проход merge, решивший, что
делать нечего, отбросил бы записи лога, покрывающие реальные данные. Проход
повторяется не более четырёх раз, потому что split переносит буферизованные записи в
листья, которые проход уже посетил.

## Слой кэша

Файл: `pkg/oneleafdb/cache.go`

### Структура

```go
type valueCache struct {
    mu       sync.RWMutex
    maxBytes int64
    used     int64
    items    map[string]cacheEntry
}

type cacheEntry struct {
    value []byte
    epoch uint64
    size  int64
}
```

Бюджет по умолчанию — 5 MiB (`DefaultCacheBytes`); `CacheEntries` переводится в
байтовый бюджет из расчёта 160 байт на запись.

### Шардированная инвалидация по эпохам

Счётчик инвалидации живёт на `DB` и разбит на 256 шардов, выбираемых по хэшу ключа:

```go
const cacheEpochShards = 256

func cacheShard(key []byte) uint64 {
    return xxhash.Sum64(key) % cacheEpochShards
}

func (db *DB) invalidate(key []byte) {
    db.cacheEpoch[cacheShard(key)].Add(1)
    db.cache.delete(key)
}
```

Единственная глобальная эпоха, которая была у этого кэша раньше, приводила к тому,
что каждая запись инвалидировала каждую закэшированную запись: при любой смешанной
нагрузке чтение/запись hit rate падал примерно до нуля. Шардирование ограничивает
запись одним шардом, поэтому записи в остальных 255 шардах остаются пригодными. Это
стоит одного массива счётчиков и оставляет путь чтения lock-free относительно
инвалидации.

Запись по-прежнему валидна лишь пока счётчик её собственного шарда не изменился,
поэтому запись в несвязанный ключ того же шарда тоже инвалидирует её. Такова цена
отказа от отслеживания версий по ключу.

При чтении `Get` сначала считывает счётчик шарда, использует его для поиска и
сохраняет свежую запись только в том случае, если счётчик за это время не сдвинулся:

```go
shard := cacheShard(key)
epoch := db.cacheEpoch[shard].Load()
if value, ok := db.cache.get(key, epoch); ok {
    return value, true, nil
}
// ... read through the tree ...
if db.cacheEpoch[shard].Load() == epoch {
    db.cache.set(key, value, epoch)
}
```

### Формат ключа

Поиск заимствует байты ключа в качестве ключа map без аллокации; только `set`
материализует собственную строку.

```go
func cacheKeyView(key []byte) string {
    if len(key) == 0 {
        return ""
    }
    return unsafe.String(&key[0], len(key))
}
```

Случай пустого ключа выделен явно, потому что взятие адреса `key[0]` паникует на
пустом слайсе.

### Вытеснение

Произвольный порядок итерации по map, пока запись не поместится в байтовый бюджет:

```go
for c.used+size > c.maxBytes {
    for evict := range c.items {
        c.used -= c.items[evict].size
        delete(c.items, evict)
        break
    }
}
```

Значение, превышающее весь бюджет, не кэшируется вовсе.

### Владение

Кэш всегда клонирует данные и в `set`, и в `get`. Вызывающие передают представления
памяти skiplist или блока, которые могут быть перезаписаны или освобождены у него под
ногами, а вызывающий, изменивший возвращённый слайс, иначе повредил бы кэш.

## Кодирование значений

Файл: `internal/value/value.go`

### Размещение тега типа

Тег типа хранится в конце закодированных данных, чтобы итерация по префиксам ключей
могла откладывать разбор значения до момента, когда оно действительно понадобится.

```go
type Kind byte

const (
    KindBytes Kind = 1
    KindInt64 Kind = 2
)
```

### Форматы

**Bytes:**
```
[сырые байты][0x01]
```

**Int64:**
```
[varint][0x02]
```

### Кодирование

```go
func EncodeBytes(data []byte) []byte {
    encoded := make([]byte, len(data)+1)
    copy(encoded, data)
    encoded[len(data)] = byte(KindBytes)
    return encoded
}

func EncodeInt64(v int64) []byte {
    var buf [binary.MaxVarintLen64 + 1]byte
    n := binary.PutVarint(buf[:], v)
    buf[n] = byte(KindInt64)
    return buf[:n+1]
}
```

`EncodeBytes` никогда не дописывает в массив вызывающего: добавление тега на месте
испортило бы байты за пределами `len(data)` всякий раз, когда вызывающий передал
слайс с запасом ёмкости. Поскольку результат аллоцирован заново, лист отдаёт его
напрямую в `ops.NewPutOwned`, не платя за вторую копию.

### Декодирование

Сначала читается последний байт для определения типа, затем извлекается payload:

```go
func KindOf(data []byte) (Kind, error) {
    if len(data) == 0 {
        return 0, ErrEmptyValue
    }
    kind := Kind(data[len(data)-1])
    switch kind {
    case KindBytes, KindInt64:
        return kind, nil
    default:
        return 0, fmt.Errorf("%w: %d", ErrUnknownKind, kind)
    }
}
```

`DecodeBytes` и `DecodeInt64` оба падают с `ErrKindMismatch`, когда тег не
соответствует запрошенному вызывающим типу, поэтому счётчик никогда не может быть
молча прочитан как байты.

### Обоснование

Дизайн с тегом в конце позволяет итерации по префиксам ключей откладывать разбор
значений до необходимости, снижая CPU в range scans.

## Поток данных

### Путь чтения

```
1. Кэш
   - Загрузить эпоху шарда для ключа
   - Если запись существует с этой эпохой: вернуть копию

2. Дерево
   - Обрамить поиск поколением merge
   - Бинарным поиском по слайсу листьев найти владеющий лист

3. Буфер листа (оба слоя из одного снимка)
   - Put: вернуть буферизованное значение
   - Delete tombstone: вернуть not found
   - Inc: прочитать базовое значение из сегмента и добавить дельту

4. Сегмент (только если буфер не дал ответа или нужно разрешить Inc)
   a. Bloom filter: может ли содержать ключ?
   b. Индекс: бинарный поиск блока
   c. Прочитать блок в пуловый буфер
   d. Декомпрессировать LZ4-словарём, если сжато
   e. Бинарный поиск точного ключа в блоке

5. Декодировать тег значения, скопировать для вызывающего, закэшировать, если эпоха шарда не изменилась
```

Путь в коде:

```go
func (db *DB) Get(key []byte) ([]byte, bool, error) {
    shard := cacheShard(key)
    epoch := db.cacheEpoch[shard].Load()
    if value, ok := db.cache.get(key, epoch); ok {
        return value, true, nil
    }

    value, ok, err := db.tree.Get(key)
    if err != nil {
        return nil, false, err
    }
    if !ok {
        db.cache.delete(key)
        return nil, false, nil
    }

    valueCopy := make([]byte, len(value))
    copy(valueCopy, value)
    if db.cacheEpoch[shard].Load() == epoch {
        db.cache.set(key, value, epoch)
    }
    return valueCopy, true, nil
}
```

`tree.Get` отдаёт представление живой памяти skiplist или блока. Возврат его прямо
вызывающему позволил бы записи на стороне вызывающего повредить базу данных, поэтому
вызывающий получает собственную копию, а кэш клонирует данные отдельно.

### Путь записи

```
1. Взять read-сторону applyMu

2. Дописать в WAL
   - Закодировать запись с порядковым номером и CRC
   - Подготовить её в активном буфере
   - Если SyncWrites: дождаться сброса

3. Применить к дереву (всё ещё под applyMu)
   - Отвергнуть пустой ключ
   - Бинарным поиском по слайсу листьев найти владеющий лист
   - Буферизовать операцию под read-блокировкой листа
   - Если лист был отсоединён при split: разрешить заново и повторить

4. Отпустить applyMu, затем инвалидировать кэш
   - Увеличить счётчик только для шарда этого ключа
   - Удалить закэшированную запись для ключа

5. Учесть рост лога и уведомить merge-воркер
```

Путь в коде:

```go
func (db *DB) Put(key, value []byte) error {
    if err := db.backgroundErr(); err != nil {
        return err
    }

    db.applyMu.RLock()
    err := db.appendPut(key, value)
    if err != nil {
        db.applyMu.RUnlock()
        return err
    }
    err = db.tree.Put(key, value)
    db.applyMu.RUnlock()
    if err != nil {
        return err
    }

    db.invalidate(key)
    db.noteWALGrowth(len(key) + len(value))
    db.notifyMergeWorker()
    return nil
}
```

## Оптимизации производительности

### Lock-free путь чтения

Поиск нигде не берёт мьютекс: он атомарно загружает снимок листьев, выполняет по
нему бинарный поиск, читает lock-free skiplist и читает иммутабельный сегмент.
Единственная синхронизация — счётчик поколений merge, который стоит читателю двух
атомарных загрузок, а писателю — двух атомарных инкрементов на merge, и окно
которого покрывает только саму установку результата, но никогда не построение
сегмента.

### Ограниченная write amplification

Merge читает и переписывает один лист. При единственном листе, покрывающем всё
пространство ключей, каждый merge переписывал всю базу данных, и write amplification
росла вместе с размером базы; с деревом листьев переписываемый объём ограничен
`MaxLeafBytes`.

### Однопроходный split

Split режет по накопленным байтам на границе ключей прямо во время записи слитого
потока. Второго прохода нет, и медиана не вычисляется.

### Zero-copy управление буферами

Пуловые буферы с явными вызовами `Release()`:

```go
type PooledBuffer struct {
    Data   []byte
    bufPtr *[]byte
}

func (pb *PooledBuffer) Release() {
    if pb != nil && pb.bufPtr != nil {
        blockBufPool.Put(pb.bufPtr)
        pb.bufPtr = nil
    }
}
```

Паттерн вызывающего:

```go
pb, err := readFullAt(f, offset, length)
if err != nil {
    return err
}
defer pb.Release()
```

Секции, превышающие размер пулового буфера (индекс и bloom при открытии),
откатываются на обычную аллокацию.

### Lock-free декомпрессия

`Dictionary` защищает свой флаг closed через `atomic.Bool`, поэтому `Decompress`
никогда не берёт мьютекс; его берут только `Compress` и `Close`.

```go
func (d *Dictionary) Decompress(src []byte) (*PooledDecompressBuffer, error) {
    if d == nil {
        return nil, ErrNilDictionary
    }
    if d.closed.Load() {
        return nil, ErrDictionaryClosed
    }
    // Decompress without holding a lock
}
```

### Иммутабельные ключи

Skiplist хранит переданный ему слайс ключа, не клонируя его:

```go
func newNode(key []byte, op ops.Op, height int32) *node {
    n := &node{
        key:  key,
        next: make([]atomic.Pointer[node], height),
    }
    n.op.Store(&op)
    return n
}
```

Поэтому вызывающие обязаны считать ключ, переданный в буфер, иммутабельным на всё
время жизни записи.

### Общий retire-воркер

Одна горутина на дерево разбирает выведенные из эксплуатации reader'ы сегментов —
вместо одной горутины на лист. Работа для каждого листа одинакова, а дерево может
содержать их тысячи.
